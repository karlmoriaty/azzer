# Azzer 架构与逻辑审计

**日期**：2026-11-09
**范围**：全部 crate、前端、文档一致性
**结论**：**逻辑层合格，架构不合格。** 不是分层错了，是**层与层之间的线没接**。

一句话概括现状：现在的东西是**一个能力库 + 两个骨架**，还不是一个能用的产品。

---

## P0 架构断点

### 1. API 层不依赖 pipeline，N01–N16 的能力完全无法触达 ✅ **已修复**

**修复前证据**：

```
crates/azzer-api/Cargo.toml:9-10   → 只依赖 azzer-core、azzer-infer
crates/azzer-api/src/routes.rs:28  → Router 只有 /health 与 /v1/system/info
crates/azzer-api/src/state.rs:7-14 → AppState 只有 token / started_at / version
```

**后果**：R1–R6 六轮做出来的东西——N01 归一、N02 质检、N09 修复、N05 基频、N15 母带、N16 的 37 项评估——**用户一个都用不到**。它们只能在命令行里手动跑。

**已做的修复**：

| 改动 | 内容 |
|---|---|
| 依赖 | `azzer-api` 加 `azzer-pipeline` 与 `azzer-dsp` |
| 状态 | `AppState` 持有 `PipelineContext`，加 `jobs: Arc<Mutex<HashMap<String, Job>>>` |
| 端点 | `POST /v1/covers`（上传 WAV 原始字节，异步处理，返回 job_id）、`GET /v1/covers/{id}`（查状态与完整报告）、`GET /v1/covers/{id}/master.wav`（取成品） |
| 并发 | 处理跑在 `spawn_blocking`（A 入口是 CPU 密集，不能占 tokio 工作线程） |
| 体积上限 | 200MB，与 10 分钟 48k/24bit 立体声（约 173MB）留余量 |
| `/v1/system/info` | 补 `capabilities` 与 `models_declared`，前端能显示当前走哪条入口 |

**回归测试 `full_roundtrip_produces_master`**：构造 4 秒类人声 WAV → POST 上传 → 等待任务完成 → GET 取成品 → 校验 RIFF 头与非空体积。**这条测试是「能力孤岛」不再复发的守门人**。API 测试数从 4 增至 8，全过。

### 2. 前端是纯占位界面，即使 API 接上 pipeline 也发不出请求 ✅ **已修复（代码层）**

**修复前证据**：

```
apps/web/src/App.tsx:18-19        → synthPeaks(7) / synthPeaks(19)，波形是合成噪声不是真音频
apps/web/src/api/client.ts        → 只有 getJson，没有 POST、没有文件上传
apps/web/src                      → 只有 App.tsx / Waveform.tsx / styles.css 三个文件
```

**已做的修复**：

| 改动 | 内容 |
|---|---|
| `client.ts` | 加 `uploadCover`（POST 原始字节）、`getCover`（轮询）、`fetchMasterBlob`（带鉴权取成品）；补 `AEntryReport` / `EvalItem` / `Job` 的完整类型 |
| `App.tsx` | 重写为真实流程：拖拽或点选上传 → 轮询状态 → 解码真音频算峰值 → Canvas 波形 + 原生播放器 → 关键指标卡 → 链路状态 → 37 项分组清单（可折叠） |
| 假数据 | 删掉原先写死的任务列表（「夜色 · 翻唱」「epoch 12/30」），那些是硬编码占位，留着比删掉更容易误导 |
| object URL | 换成品时显式 `revokeObjectURL`，否则每处理一条就漏一段音频的内存 |
| 错误文案 | 后端错误统一转成「原因 + 下一步」，连不上服务时提示检查主进程而非「未知错误」 |

**验证状态**：

| 项 | 状态 |
|---|---|
| TypeScript 类型检查 `tsc --noEmit` | ✅ 通过 |
| 生产构建 `vite build` | ✅ 通过（29 模块，159KB JS，gzip 52.6KB） |
| API 端到端（HTTP 进、HTTP 出） | ✅ `full_roundtrip_produces_master` 通过 |
| **浏览器真实回归** | ✅ 通过，见下 |

**浏览器回归用 `scripts/e2e-web.cjs` 做**，它是一个自管生命周期的脚本（工具层会回收命令的进程树，手工起的常驻进程活不到下一步，所以脚本自己 spawn serve、自己 spawn vite、自己等就绪、自己杀）。跑一套 10 项断言：

```
空态：渲染上传区 ✓｜连上后端 ✓｜未出现「连不上」✓｜显示「未声明模型」✓
结果态：显示积分响度 ✓｜真峰值 ✓｜评估分组 ✓｜链路 ✓｜不残留上传区 ✓
       页面数值与后端一致 ✓（页面 -14.12 / 后端 -14.124）

冷启动实测：5 秒源 544ms，输出 -14.124 LUFS / -1.099 dBTP，37 项全部返回，成品 503KB RIFF 合法
```

**中途两次误读，都是 PowerShell 的 GBK 解码造成的**，值得记下来：

1. 把 `elapsed_ms=21`（缓存命中）读成「5.0s」，照着错数字排查了 20 分钟不存在的 bug；
2. 把 `elapsed_ms=544`（冷启动）读成「5444」，一度以为脚本清缓存没生效。

结论：**核对数值一律用 Node 直接读 JSON，不看 PowerShell 回显的中文行**。

**顺手改的一处 UI**：`elapsed_ms` 小于 1 秒时改用毫秒显示（`544ms` 而不是 `0.5s`）。21ms 显示成 `0.0s` 会让人以为根本没跑。

**同时给页面加了 `?job=<id>` 恢复能力**：刷新不丢结果，也让验证脚本能截到「处理完成」的界面而不是空态。

## P1 抽象未落地

### 3. `Engine` trait 是死代码

**证据**：

```
crates/azzer-core/src/engine.rs   → 定义 trait Engine { id, version, adapter_hash, supports }
crates/azzer-infer/src/runtime.rs → 只有 probe_runtime / runtime_ready / cuda_available，无 Engine 实现
全项目 grep "impl Engine"          → 只有 NoEngine 一个
```

**判断**：M0 留接口是合理的，但到 R6 仍无第二个实现，说明这个抽象**还没被现实检验过**。pipeline 里每个节点都把 `EngineDescriptor::of(&NoEngine)` 抄进幂等键，实质等价于常量。

**风险**：M2 接第一个真实模型时，如果发现 `supports(role)` 这个形状不够用（很可能——真实引擎还要报显存、并发度、支持的采样率），就得改 trait，进而改所有节点的幂等键算法，历史缓存全部失效。

**处理建议**：不删（M2 要用），但要认清它现在是「设想中的协议」而不是「已验证的协议」。

## P2 文档与语义缺口

### 4. 六层定义没有落到文档，也没有 crate 映射 ✅ **已修复**

**修复前**：v3.2 全文只有 §5.1 一句提到「L2（编排层）与 L4（引擎层）」，完整六层只存在于项目记忆里，代码里没有任何地方使用层编号。

**已做的修复**：

| 产出 | 内容 |
|---|---|
| `docs/Azzer-分层映射.md` | 六层定义、crate 映射、允许/禁止的依赖方向、每条禁止项对应的具体后果 |
| `azzer/scripts/check-layering.cjs` | 解析各 crate 的 `Cargo.toml`（含 dev/build），逐条比对禁止项；输出实际依赖图；反向检查孤岛 |
| `azzer/scripts/check-all.cjs` | 一键：分层 → Rust 测试 → 前端类型检查 → 前端构建 |

**当前检查结果**（六层全部无越界）：

```
azzer-core      L3/L6 契约与资产   ← dsp, infer, pipeline, api
azzer-dsp       L5 引擎（DSP）     ← pipeline, api
azzer-infer     L5 引擎（推理）    ← api
azzer-pipeline  L4 调度            ← api
azzer-api       L2 编排接口        ← shell
azzer-shell     L1 体验宿主        ← （入口，无人依赖）
RESULT: PASS
```

**为什么这条值得做**：脚本守的第一条是「L4 调度层不许直接 `use ort`」。M2 接 ONNX 时这条最容易被图方便破坏，而且**违反了编译照样通过**，code review 也未必看得出。现在它是一条会失败的检查。

**尚未机械保证的三条**（写在文档末尾，只能靠人守）：L3 不含采样率与模型名、L4 走 `Engine` 协议而非直接调用实现、L1 不直接拼 HTTP。第二条要等 M2 有真实引擎才谈得上检验。

### 5. N16 的 f0 语义有一处隐含假设没写明

f0 是在 **N09 的输出（母带前）** 上提取的，而 N16 评估的是 **N15 的输出（母带后）**。母带只做 EQ / 压缩 / 限幅，不改变音高，所以 f0 仍然有效——但这是**隐含假设**，代码和文档都没写。若将来母带链加入任何变调环节，这个假设会静默失效。

## 一处需要说明的判断

有人会说「界面按偏好最后做，所以 API 没接 pipeline 不算问题」。

这个说法在 M0 成立，在 M1 不成立。区别是：M0 的目标是「工具链跑通」，命令行能跑就算达成；M1 的目标写的是「**有可用的单链**」，而「可用」的定义里包含「用户能操作」。目前的状态是「引擎能跑，但没有驾驶舱也没有传动轴」——这不该被当成「界面还没做」轻轻带过，因为缺的不是界面，是**接口**。
